Lessons from that session, so you don't pay for them again:
- Anything inside an element with `role="dialog"` swallows keys: the global handler ignores them. Popups that the app's keys drive are `role="group"`.
- The legend bar keys its React nodes by label: two items with the same label leave a stale keycap behind.
- The Bash tool's heredocs eat `\n` and backslashes in scripts. Write scripts with the Write tool; fix regexes with Edit.
- A walkthrough pressing `Ctrl+Enter` inside the full look's folder dialog once **started a real card** (worktrees, a session). Add folders in tests by typing a path into the simple look's Folders tab, never through the full look.
- A blanket word rename across the code broke identifiers; a prose-only pass (string literals with a space in them, JSX text) is the safe shape.
- Playwright's `?` is `Shift+Slash`; `press('+')` works for the add-context key.

## The job: two changes to the new-session popup

### 1. Make the popup take up most of the page
Today (`NewCardSimple.tsx`) the popup is inset 16–24px on each side but its content sits in a 760px column, so most of the panel is empty. The owner wants the popup to **use the space**: inset about 16px, the content column much wider (1100px or so), the ticket card, chips, opening message and session settings laid out to fill it (two columns at a wide window is fine: ticket and context on the left, opening message and settings on the right, one column under about 1100px). Keep the keyboard order (↑ ↓ down the blocks) matching the reading order. Keep the full look untouched.

### 2. Replace "Your note" with the opening message, chosen from saved prompts that fill in the context
The owner's words: "I usually write a prompt (or have Claude write a prompt for me based on my initial message so it's better formatted than what I could do) like *Please review {jira card(s)} and take that into context, you'll likely need {repo}, {repo} and extracted business logic from {folder}.* I'd likely also include some instructions on creating a new feature branch/worktree... so these prompts should include the context we provide during the intake of a new session and be something that is editable (eventually versionable? after MVP). We should be able to select prompts from a dropdown that are used (or freeform input text for that opening message)."

What to build:
- **The block is "Opening message"**, in place of "Your note". It is the first thing Claude is told (today `launch.message`, the prompt argument to `claude`; the context itself still arrives through the SessionStart hook, so the message can be long but keep it to a prompt, not the packet). The "Your note" text (`packet.note`, the hook's *From you* section) goes away from the simple look; the full look keeps it.
- **A dropdown of saved prompts** at the top of the block (a key to open it, ↑ ↓ Enter; a row in `?`), plus **"Write your own"**. Picking a prompt renders it with the placeholders filled from the card as it stands and puts the result in the editable text box. Editing the text detaches it from the prompt (the dropdown then says "Edited from: Review and plan"); picking the prompt again re-renders it. Changing the context afterwards (adding a repo, changing the ticket) re-renders an unedited prompt live, so the message always matches what was picked.
- **Placeholders**, filled from the composer: `{{ticket}}` (key and title), `{{tickets}}` (the card's ticket plus related ones, as a list), `{{repos}}` (the repos Claude can see, by name; the one it starts in first), `{{home}}` (the repo it starts in), `{{folders}}` (folders from disk), `{{lane}}`, `{{branch}}` (the card's branch name), `{{kind}}` (Develop / QA / Code review). Unfilled or empty ones render to nothing and the preview says so. Put the renderer in a pure module with unit tests (`shared/prompts.ts`: `renderPrompt(template, context)`; the context comes from the composer the way `howFacts` reads it in `web/simple-model.ts`).
- **Saved prompts live on the server** (SQLite, `server/store.ts`, like settings and workspaces) and are shared through the lane file later if the owner wants (not now). Shape: `{ id, name, body, kind?: 'build' | 'qa' | 'review' }`; a prompt with a kind is offered first for cards of that kind. Protocol: `prompts` (server → page, the list, sent with `hello` and on change), `prompt.save`, `prompt.delete`; bump `PROTOCOL`. Ship with **three defaults** the first time (written to the store, so they are editable like any other): *Review and plan* (review the ticket(s), the repos it will need, the folder of business logic, plan before changing anything), *Fix a bug* and *QA this change*, each using the placeholders above and saying the worktree is already made (the card makes it; Claude must not create branches or worktrees itself).
- **Editing prompts**: a small dialog from the block (a key; a row in `?`): the list, `n` new, `e` edit (name, kind, body with the placeholder list shown beside it and a live example rendered from the current card), `Delete`, Esc. "Save as a prompt" from the text box turns an edited message into a new prompt. Versioning is explicitly after the MVP: don't build history, but keep `updatedAt` on each prompt.
- **"Have Claude write it" (optional, after the rest works):** a button that sends the owner's rough text plus the rendered context to a cheap model through the Agent SDK on the server (`query()` with Haiku, one turn, no tools) and puts the result in the box. Ask the owner before building it; it spends tokens.
- Keys: everything above needs a key, a legend entry (the legend is hidden by `web/slim.ts` but still computed and tested) and a row in `LINE_SECTIONS`. Keep the popup's keycaps few: Esc, Ctrl+Enter, `?`.

Verify as before: unit tests for the renderer and the store, `pnpm typecheck`, the unused-locals check, a scripted Playwright walkthrough on an isolated server (seeded like `walk-simple.cjs`) that picks a prompt, sees the ticket and repos filled in, adds a repo and sees the message follow, edits the text and sees it detach, saves it as a prompt, and starts nothing.
