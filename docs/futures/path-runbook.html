Runbook: your loop is the interface

One piece of work at a time, walked through your loop as a checklist in plain words: ticket, context, plan, build, try it, fix, ship. Each step says what happened and what to do next. The loop is a recipe your team can edit, including how your app starts for a smoke test.

A day with it

  1. 08:55

    Two new tickets sit in the inbox, pulled from Jira. Drag SHOP-151 onto Start a job. It lands on Context with web-app and cdn-worker attached, because the ticket belongs to Storefront.

  2. 09:00

    Context lists the ticket, the Storefront notes and the repos. The bar says Claude will start 38% full. Press a to start planning.

  3. 10:12

    The plan is five plain steps. Press c to add "keep the old image URLs working", then a to approve.

  4. 10:20

    Build ticks through the plan while you start PAY-88. When PAY-88 turns amber, Claude is asking 200 or 409. Press 1 and go back.

  5. 10:48

    Try it. Press r: the app installs, seeds and starts on localhost:5173, the way web-app always starts. The checklist comes from the ticket.

  6. 10:55

    Three checks pass. The hero image still jumps. Press x, write one line, press Enter. That is round 2.

  7. 11:20

    Round 2 is done. Check the one item again. It passes.

  8. 11:32

    Ship shows the commit, branch, PR and Slack post, all written from the ticket and plan. Press s. PR #418 is up and #storefront-reviews has the link.

  9. 15:00

    The team lead adds "Run e2e tests" after Try it in the Storefront loop. New jobs get it.

What it asks of you

  • Only decisions. Approve a plan, answer a question, pass or fail a check, ship. Everything else is Claude or the recipe.
  • One next action. The current step is always lit, and the legend shows the keys for it.
  • Smoke testing is a real step. The run recipe is detected from package.json or compose.yaml, and you can edit it. Monorepos, Docker, seeded logins and VPNs all fit.
  • Rounds you can undo. Each fix round is a checkpoint. u rewinds the files to before it.
  • A shared loop. Each workspace keeps its own recipe, so the whole team works the same way.

Good at

  • Someone new can finish a ticket end to end and say what happened at each step.
  • Smoke tests stop being "spin it up somehow": the recipe starts the app the same way every time.
  • Acceptance criteria turn into the test checklist, and failed checks turn into the fix message.
  • Shipping is one key: commit, PR and the Slack post come from the ticket and plan.

Trade-offs

  • One job is in focus. Running five at once is possible from the rail but not what the screen is built for.
  • It runs its own sessions. If you live in terminals, o hands off, and the steps then only follow along through hooks.
  • A fixed loop feels slow for a quick question. A "no loop" job would be needed for that.
  • Jira, Trello and Slack each need a token and sometimes an admin's approval.

Drops

  • The three-column session list as the home screen. The rail replaces it.
  • Chat as the main view. Claude's questions arrive as cards, and a full transcript is one key away.
  • The number pad and mode cycling. Plan-first and the approval style become parts of the recipe.

What Claude Code allows: this path runs its own SDK sessions, so it gets file checkpoints for undo and full control of each step. There is no supported way to attach to a session already running in a terminal. Once a job is handed to a terminal, documented hooks can report its events and a SessionStart hook can inject the job's context. A channel (research preview, needs a dev flag) could push messages into that terminal and relay its approvals. Transcripts are read through the SDK's getSessionMessages.
