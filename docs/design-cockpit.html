Where a repo can go

Onto a domain
The repo joins that domain. New sessions there can use it, and its sessions from the terminal show up in the domain.
Onto a session
Claude can read and edit it alongside the session's own repo, for example to change an API and the app that calls it together.
Onto "New session"
Starts a session in that repo, in the current domain.
No mouse? Select the repo in the library with the arrows, press + and pick a domain or session from the list, with its number.

Home: three columns you walk with the arrows

  • Domains → sessions → preview, like Finder's column view. ← → moves between columns; the focused one is lifted and outlined, the others dim.
  • Every row shows its key. Domains are 1–9; 0 is "Unsorted" (sessions outside any domain, including terminal ones).
  • The preview answers an approval without opening the session, as the Inbox does today.
  • The repo library is scanned from source folders you choose (e.g. D:\repos). Each card shows its domain(s).
  • A bottom legend of 6–7 large keycaps replaces today's 9 small hints, and changes with the focused column.

Drag a repo

  • Drop on a domain: the repo joins it. Drop on a session: it becomes extra context for that session. Drop on New: a session starts there.
  • Keyboard version: select the card, +, then pick a target by its number.
  • Under the hood, extra context is the SDK's additionalDirectories. A running session picks it up with a quick resume; the conversation is kept.

Session: the number pad is on screen

  • The board is drawn as a real number pad, including 0 (home), . (talk), +/− (groups), /, * and Enter, so what you see is what's under your hand.
  • Keys are workflows: named instructions, some multi-step ("Ship it: tests → review → PR"). The domain's workflows come first.
  • The context bar shows every repo Claude can work in, and is a drop target.
  • Steps are in plain words and say which repo they touch.

Approvals

  • Plain question first, risk rating, what it touches, then the raw command.
  • Y A N work even while you're typing in the message box, as long as the box is empty, so the Tab step is gone.
  • "Always" says exactly what it will always allow, and where.
  • Risk (safe / changes / careful) comes from a small, tested rule set over the tool and command.

Setting up a domain

  • Name, colour, repos picked from the library (Space), and a home repo where new sessions start.
  • A repo can be in several domains.
  • Workflows come from starter sets, or copied from another domain. A domain exports as one JSON file, so a team shares its setup the way repo packs work today.

First run

  • Teaches the four key groups as physical key clusters, so it clicks that the keyboard is the interface.
  • Then goes straight into creating a domain from your repo folder, so the first screen is never empty.

Open questions

  • Name: "Domain", or "Workspace" / "Space"?
  • Theme: dark by default for an all-day tool, light available. OK?

How it fits together

Domains

  • A named group of repos, with a colour, a home repo and its own workflows.
  • Sessions belong to a domain by their folder, so terminal sessions sort themselves too.
  • Stored in the local SQLite file; export and import as JSON.

Repo library

  • One or more source folders, scanned for git repos (name, branch, last change).
  • Rescans on focus; no background indexing of your code.
  • Repos outside any source folder can still be added by path.

Keyboard

  • Everything that works today keeps its key: numpad, Alt+N, Y/A/N, Esc to stop, Ctrl+B, Ctrl+K, ?, rebinding.
  • New: ←→ columns, 1–9 domains on home, + add repo, D new domain.
